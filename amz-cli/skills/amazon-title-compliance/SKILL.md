# Amazon Listing 文案优化

按 2026-07-27 新规改写三个字段：**标题（≤75 字符）**、**商品亮点（≤125 字符）**、**五点描述**。事实只能来自素材，写入必须经用户同意。

**不管广告**（投放、竞价、否词、预算）——那是 ads 相关 skill 的活。

## 两条铁律

1. **只用素材里的事实，一个字都不许补。** 材质、颜色、尺寸、重量、件数、认证、产地这类物理属性，只有在素材里**有出处**时才能写。**查不到就先问运营**——他手里有实物和供应商资料，多半知道；问不到才绕开不写，并记进 `omitted`。任何时候都不要写成「可能」「据称」。虚假描述会导致 listing 下架。
   ⚠️ 市场数据和竞品标题**不是素材**——它们只能影响用哪个词，不能提供任何关于本商品的事实。
2. **写入前必须由用户点头。** 生成稿 ≠ 已写入。你要把「当前值 → 新值 + 字符数 + 舍弃项 + 矛盾项」摆出来，等用户明确说「写」「提交」「确认」才进入写入步骤。用户没表态就停在那里，不要自作主张预览或提交。

事实判定、数出处、违禁词、关键词归位的完整规则见 [references/writing-rules.md](references/writing-rules.md)。核实过的新规条款和来源见 [references/rules-2026.md](references/rules-2026.md)。

## ⚠️ 红线：schema 通过 ≠ 合规

**亚马逊的 schema 上限是 API 上限，政策上限比它严得多。** API 收得下的东西，亚马逊照样按政策改写或删除。

| 字段 | schema（API 收得下） | 政策 | 证据 | 校验器 |
|---|---|---|---|---|
| 标题 `item_name` | 200 | **75** | 公告 + schema description 提及 75 | **error** |
| 亮点 `title_differentiation` | 125 | 125 | schema maxLength 实证 | **error** |
| 五点单条 | 700 | 255? | **只有第三方文章** | warning |
| 五点条数 | 10 | **5** | 多方一致 | error |

**规则按证据强度分级**——一手证据（schema `description` / 亚马逊公告）才判 error；只有第三方来源的判 warning 并标注 `evidence: third-party`。

> 五点 255 就是这么降级的：实测同一店铺 30 条在架五点 **57% 超过 255**（最长 382），且 250–260 区间**一条都没有**——看不到任何被截断的痕迹。没有证据支撑就不该拦人干活。硬上限改用 schema 的 700（API 真会拒的那条线）。

后果很实在：191 字符的标题、350 字符的五点，**官方 `VALIDATION_PREVIEW` 会返回 `VALID`、写入会成功**，然后被亚马逊 AI 悄悄改掉，你还不一定收到通知。

**所以 `--dry-run` 拦不住政策违规，`check-copy.mjs` 是唯一那道闸。** 不许拿"dry-run 过了"当合规证据。

## 交付的是一整套，不是补丁

| 字段 | 属性名（以 schema 为准） | 上限 |
|---|---|---|
| 标题 | 通常 `item_name` | **75 字符**（媒体类目 200） |
| 商品亮点 | 新字段，名字随产品类型而异 | **125 字符** |
| 五点 | 通常 `bullet_point` | **5 条**（至少 3 条才算一套） |

**这三个字段是咬合的整体，一次全部重写。** 标题砍到 75 字符，删掉的次级词要由亮点承接；亮点内容一变，五点就得重新分配维度避免重复。**只改其中一个，另外两个必然和它对不上。**

所以校验一律带 `--complete`，缺任一字段直接报 `E_INCOMPLETE_SET`。

> ⚠️ **这意味着会覆盖运营已经写好的五点和亮点。** 所以汇报时必须逐字段展示「当前值 → 新值」，让用户能对单个字段说"这条保留原样"。别默认用户会全盘接受。

**后台搜索词默认不做**——模型在猜买家怎么搜，没有真实搜索数据支撑。用户明确要求才写，并说明这层限制。

不改 A+、QA、主图、后台属性字段。

## 运行环境（先看这个）

**[references/runtime.md](references/runtime.md) 在动手前必读。** 三件事最容易调错：

- amz-cli 的 **MCP 没有任何读数据的工具**（只有 `inspect_listing_schema` 和 `prepare_*`/`apply_*`）。读当前标题、属性、报表**一律走终端**，不要猜工具名。
- 多店铺环境下 `account` / `--account` **必填**，店铺不明确就先问。
- 校验脚本在**本 skill 目录**下，不在项目仓库里，要用绝对路径调。

## 流程（单条和批量共用）

### 1. 定范围

明确**店铺、站点、要改哪些 SKU/ASIN**。多店铺时店铺不明确就只问店铺，不要靠 ASIN 猜、也不要遍历店铺去找。

- 1 条 → 走 [references/single.md](references/single.md)
- 2 条及以上 → 走 [references/batch.md](references/batch.md)（单批最多 50 条，超出拆批）

### 2. 取素材（只读，走终端）

**别手写提取脚本** —— 用 `extract` 子命令，它把素材一次填满：

```bash
node "<本 skill 目录>/scripts/check-copy.mjs" extract \n  --file "<listing sku 的 JSON 或 listing batch 的 jsonl>" \n  --marketplace <站点> --highlight-attr <schema 查到的亮点属性名> \n  --out "<草稿骨架.json>"
```

它产出的骨架里 `title`/`highlights`/`bullets` 留空（那是你要写的），其余全部填好，`attributes` 和 `valueTemplate` 也自动生成。

> 为什么要有这一步：漏字段这类失误**只能靠取消手写提取来根治**。实测手写脚本漏掉 `product_description` 一次，丢了「颜色是涂层」这个真事实，也没发现改完后描述会和新五点矛盾。文档里写「别漏」没用——那是清单型规则，散文里活不下去。

它会取到的字段：

```
item_name  title_differentiation  bullet_point  product_description
brand  color  material  unit_count  special_feature  productType  MSKU
```

⚠️ **`product_description` 最容易漏** —— 它不是你要改的字段，所以按"我要写什么"去提取时它不会进视野。但它是 `<listing_local>` 素材，漏读会丢事实（实测丢过「颜色是涂层」），也看不出改完后的矛盾。

⚠️ **`special_feature` 这类结构化属性经常是第二个独立出处** —— 实测 `special_feature: Bruchfest` 让"不易碎"从"单一自述、不敢写"变成"可以写"。

取数命令见对应的 single / batch 参考文件。

**素材必须按来源分区喂给自己**（catalog / 本站 listing / 他站 listing / 内部 ERP / 变体兄弟）——「数独立出处」这套判断建立在分得清来源之上，混成一张表就失效了。

### 3. 选词（可选，但砍标题时很值）

标题从 190 砍到 75，最难的是**留哪个主词**。有依据就别拍脑袋：自家广告搜索词报表 > 市场 MCP > 现有素材。见 [references/keyword-choice.md](references/keyword-choice.md)。

⚠️ **外部数据只能影响用哪个词，不能提供任何关于本商品的事实。**

### 4. 生成

按 [references/writing-rules.md](references/writing-rules.md) 写**一整套**：标题 + 亮点 + 五点。

顺序不能反：**先定标题的主词 → 亮点承接标题装不下的次级词 → 五点覆盖剩下的维度。** 倒着写必然重复，而且重复的代价不对等——亮点只有 125 字符且显示在搜索结果页，被五点里的话占掉就是白扔黄金位。

素材里查不到又会进标题的属性（颜色、材质、尺寸、认证）→ **先问用户**。批量时攒成一份待确认清单一次问完，不要逐条打断。

### 5. 机器校验（不可跳过）

**字符数不靠自觉。** 自己数「68 字符」实际经常是 82，德语复合词尤其严重。生成完一律跑：

```bash
node "<本 skill 目录>/scripts/check-copy.mjs" check --file "<草稿.json>" --complete
```

脚本零依赖，只用 Node 内置模块。**路径是本 skill 目录，不是项目仓库路径**（见 [references/runtime.md](references/runtime.md)）。

退出码非 0 就是没过。**带着具体错误回第 4 步重写**，不要手工微调字符数糊弄过去。草稿 JSON 的字段说明见脚本的 `--help`。

跑不了脚本时**不要自己数顶上**——如实说明「字符数未经校验」，请用户核对后再决定。

### 6. 报给用户，等确认

**用命令生成对照表，不要手写**——手写会漏（实测漏过五点原文，用户不得不追问）：

```bash
node "<本 skill 目录>/scripts/check-copy.mjs" report --file "<草稿.json>"
```

它会输出逐字段「当前值 → 新值」（五点逐条）、**现状体检**（当前值有几个问题、分别是什么）、新版校验结果、`omitted`、`conflicts`、选词依据。要它完整，草稿里得有 `currentTitle` / `currentHighlights` / `currentBullets` / `keywordEvidence`。

**现状体检那一行是说服力最强的材料**——「现状 13 个问题：标题超限、标题没品牌、5 条五点超政策线、5 条五点全大写」比任何解释都管用。

贴出报告后**停下**。这是铁律二。

### 7. 写入（用户同意后）

先查卖家专属 Schema 拿真实属性名和结构，**不要凭记忆拼 patch**：

- **有 MCP**（Cherry Studio）：优先用只读 `inspect_listing_schema`。先传 `query` 按「商品亮点 / Item Highlights」这类业务名称搜索，**唯一匹配后**再用 `attribute` 读完整定义。
- **只有终端**：`listing schema --account <店铺> --marketplace <站点> --product-type <类型> --grep highlight`，再 `--attribute <真实属性名>`。

标题字段通常是 `item_name`，商品亮点是新字段、名字随产品类型而异。**搜不到或匹配多个时列出证据问用户，不得换几个猜测名反复试**——「试了几个都失败」不能证明 API 不支持。

### 🔑 必读 schema 的 `description`，它是最高证据

拿到属性定义后**不要只看 `maxLength` 和 value 结构就走**。`description` 是**亚马逊针对这个卖家、这个站点、这个产品类型写的规范原文**，等级高于本 skill 的任何文档和你的记忆。

实测一次就拿到五条规则（DE 站 `DRINKING_STRAW`）：

> `title_differentiation`：「给出产品特征或利益导向的**短语，不要完整句子**」·「该信息**仅在商品名称低于 75 字符时才显示**」·「**不要重复**商品名称里已有的信息」
> `bullet_point`：「**不要使用全大写单词或缩写**」·「**请勿**用于材质成分、护理说明或原产国，这些有专门字段」

**做法**：把 description 原文摘出来，逐条对照本次要写的内容；**与 references 里的规则冲突时以 description 为准**，并在汇报里说明。不同产品类型的 description 可能不同，别把一个类型读到的结论套到别的类型上。

拿到真实属性名和当前值的对象结构后，生成 patch 文件：

```bash
node "<本 skill 目录>/scripts/check-copy.mjs" patches --file "<草稿.json>" --out-dir "<目录>" --account <店铺>
```

然后按通道，详见 [references/writing.md](references/writing.md)：

- **MCP 通道（Cherry Studio 默认走这条）**：`prepare_listing_update`（`account` 必填）→ 报预览摘要 → `apply_listing_update`，由审批卡人工把关。**不要给用户 CLI confirm 命令**——终端 confirm 要求交互式 TTY，运营在 Cherry 里跑不通。
- **只有终端时**：你做到 `listing update --dry-run` 为止，把带预览令牌的 `--confirm` 命令交给用户本人在 PowerShell 跑。**写操作的最终执行必须由人在交互式终端确认，你跑不了，也不要尝试绕过。**

## 汇报口径

每条至少给出：

| 项 | 内容 |
|---|---|
| SKU / 站点 | |
| 标题 | 当前值 + 字符数 → 新值 + 字符数（校验器算的，不是估的） |
| 商品亮点 | 当前值（多半是空）→ 新值 + 字符数 |
| 五点 | **逐条**当前值 → 新值。原来有几条就摆几条对照 |
| 舍弃项 `omitted` | 因素材不足没写的信息 |
| 矛盾项 `conflicts` | 素材互相打架的地方、采用了哪个、依据 |
| 校验 | 通过 / 警告项 |

批量时给汇总表 + 明细文件路径，不要把几十条原文全倒进对话。

**必须给用户留否决单个字段的余地。** 整套重写会覆盖运营已经写好的东西，摆出对照后加一句：「哪条想保留原样，告诉我，我把它从这次写入里去掉。」用户点名保留的字段，从 patch 里删掉那一项——**不要整条跳过**，其余字段照常写。

### 改完要提醒的两件事

**① 回查一致性。** 改标题会**制造新的矛盾**——原来标题写 `Beige`、后台 `Color` 属性也是 `Beige`，现在标题砍掉了颜色或换了说法，两边就对不上了。提醒用户核对：

- **后台属性字段**（Color / Material / Size / Item Weight…）——和新标题、新亮点说的是不是同一件事
- **图片文字层**——副图上印的尺寸/规格和新标题打架吗（图上 `16 inch`、标题 `15.7 inch` 就是矛盾，AI 和买家都看得见）

这两处我们读不到（`listing sku` 不返回图片文字，属性要另查），所以只能提醒，不能代劳。

**② 生效节奏，别急着回滚。** 关键词收录约 **24 小时**；Rufus/COSMO 的语义推荐层要 **7–14 天**。改完三天没动静是正常的，这时候回滚只会把两边都白折腾一次。

**写操作结果如实转达**：`processingStatus: SUBMITTED`、`ACCEPTED`、`immediateReadback` 都**不**代表前台已生效——亚马逊会继续异步处理目录数据，回读可能仍是旧值。有 `readbackError` 一并说明，不要略去，也不要因为不确定就自动重试写入。
